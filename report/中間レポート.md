# 1. 今回取り組む課題の内容（課題 1）

## 1.1 背景となる問題意識

・今の Google Maps やグルメサイトでは、店舗ごとの「自分に合った費用感」が分かりにくい。さらに、評価やレビューは不特定多数の投稿に依存しているため、信憑性が低いケースが多い。そこで、友達や身近なコミュニティの実体験に基づく情報を共有できれば、自分に近い視点の情報が得られ、信頼性も高まる。また、自炊管理は単独では継続しにくいが、SNS 型の仕組みで「承認欲求」を満たし、仲間から「いいね」やコメントをもらえることで継続モチベーションを高められる。

## 1.2 社会的な意義・普遍性

- **対象ユーザー**
  - 大学生、若年層、外食が多い人、SNS 慣れした人
- **社会的意義**
  - 予算感や好みに近い情報が得られ、店選びの失敗が減る
  - SNS 的な承認があることで、自炊や食習慣の継続意欲が上がる
  - 仲間との共有が増え、アプリ内での交流・リピート利用が促進される
  - 個別の体験に基づいた情報が集まることで、従来の一方向レビューより価値が高まる
- **普遍性**
  - 例：友人ベースでの意思決定は飲食以外にも応用可能
  - 例：同様の課題は他の地域・世代にも存在

## 1.3 既存の解決方法の調査結果

- **既存サービス調査**
  - Google Maps
  - 食べログ
  - Instagram や Twitter の位置情報投稿
- **既存手法の長所・短所**
  - 長所：評価数が多い、検索機能が充実
  - 短所：信頼性が低い、友人の体験が分かりにくい
- **Who eats が目指す差別化**
  - 友人や身近なコミュニティにフォーカス
  - 投稿中心の地図表示

> 図表例：既存サービスの比較表 / 課題の流れ図 / 現行ユーザー行動の課題図解

# 2. 課題解決方法（課題 2）

## 2.1 問題の具体化・何をどこまで解決しようと考えているか

- **解決対象**
  - 友人やつながりのある人の食体験を地図上で見える化
  - 位置情報を使った店舗ピン表示
  - 投稿に基づく店舗選択支援
- **範囲**
  - MVP では「地図表示」「投稿」「認証」「プロフィール」「お気に入り」などを中心に実装
  - まずは大学生向けの利用シナリオに絞る

## 2.2 解決方法のアプローチ・利用技術の概要と調査

- **アプローチ**
  - Flutter でクロスプラットフォーム開発
  - Supabase で認証・DB・ストレージを統合
  - Google Maps / Places API で地図・店舗情報を取得
- **利用技術**
  - Flutter（UI・画面構成）
  - Supabase（ユーザー・投稿・フォロー管理）
  - Google Maps Web API / Places API（地図、店舗検索、詳細）
  - dotenv / 環境変数（API キー管理）
- **調査結果**
  - Supabase は Postgres と Storage を簡単に扱える
  - Google Maps は CORS や API キー管理に注意
  - Flutter Web では .env の扱いとブラウザセキュリティが重要

> 図表例：システム構成図 / 技術マップ / API 呼び出しフロー

## 2.3 実現に向けたシナリオ

- **ユーザーシナリオ例**
  1. ユーザーがアプリを起動し、ログインまたは新規登録
  2. 地図上に友人の投稿から得た店舗ピンが表示される
  3. 店舗をタップすると詳細と友人レビューが表示
  4. 気になる投稿をお気に入り登録できる
- **データフロー**
  - 起動 → Supabase からフィード取得 → マップ表示
  - 投稿作成 → 写真アップロード → DB に店舗・投稿情報保存
- **今後の拡張シナリオ**
  - フォロー機能の強化
  - ホットスポット表示
  - 自炊投稿対応
