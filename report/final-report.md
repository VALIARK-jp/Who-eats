## 1. 課題1・2の概要

### 1.1 社会課題（課題1）

大学生の **一人暮らし開始** に伴い、食事の管理が困難になり **偏食・食生活の偏り** が続く課題を取り上げた。当初は自炊管理アプリを想定したが **持続しない** ため、**日々投稿しやすい SNS 型** の食事共有に設計を転換した（[who-eats-narrative.md](./who-eats-narrative.md)）。

### 1.2 解決方針（課題2）

**Who eats** は、自炊・外食を問わず食事を記録し、友達と共有することで **偏食を防ぎ、続く習慣** を支える。**Flutter + Supabase（OSS／無償枠）** で実装。地図・友達フィードは外食選択と継続の **手段**。課題3では **ログイン→投稿→友達のフィード→振り返り** のデモを目標とした。

## 2. 設計・作成したシステムの説明

### 2.1 設計の意図とシステムの概要

**設計意図**

- データの主役を「店の評価」から **「人の投稿」** に置く。
- 信頼境界を **フォロー関係・RLS** で表現し、見せたい範囲だけをフィードに載せる。
- 授業期間内で変更に強いよう、**クリーンアーキテクチャ寄り** の層分けを採用。

**システム概要**

| 層 | 役割 |
|----|------|
| Presentation | 5タブシェル（ホーム・友達・撮影・記録・プロフィール）、地図・フィード UI |
| Domain | エンティティ、UseCase、Repository インターフェース |
| Data | `SupabaseSocialDataSource`、Places API、モック |
| Infrastructure | Supabase Auth / PostgreSQL / Storage、マイグレーション |

## 4. 開発における苦労点

### 4.1 最も苦労した点

**Row Level Security とフィード表示範囲の整合**

クライアント側で「友達」「近い人」フィルタをかける一方、DB では RLS で閲覧可能な行だけを返す必要がある。RPC で近い人のユーザー ID 集合を取得し、クエリと組み合わせる設計まで試行錯誤した。

### 4.2 次に苦労した点

**地図 UI と 3D ピン（WebView）のパフォーマンス**

Google Map 上に WebView で 3D ピンを重ねる構成は、特に iOS で JS ペイロードサイズやフレームレートの問題が発生した。パン・ズーム中は FPS を下げ、停止後に戻すなどの対策を実施した。

### 4.3 その他

- マイグレーションの班内共有タイミング（未適用環境での RPC 不足）
- コメント一覧での著者情報 embed の不整合 → データソース層で修正

## 5. 未解決・残課題と今後の展望

### 5.1 授業スコープで未実装の機能

| 項目 | 説明 |
|------|------|
| **AI 画像解析** | 投稿写真から食品を推定し、食事の **偏り** を分析・可視化 |
| **食事回数管理** | **1日1・2・3食** の記録・リマインド |
| **栄養士スポンサー** | 監修・相談窓口・大学連携による持続可能な運営 |

### 5.2 事業・スポンサー計画（展望）

- **スポンサー候補**: 管理栄養士、栄養士会、大学保健センター、健康・食品関連企業
- **相互メリット**: スポンサーは大学生への健康啓発・アプリは専門監修と信頼性
- **収益モデル（案）**: スポンサーシップ、大学パッケージ、将来のプレミアム分析（基本機能は無償維持）

### 5.3 その他の技術的残課題

| 項目 | 原因 |
|------|------|
| ストア公開 | 授業スコープ外 |
| 「近い」の定義 | 実装は2ホップ（時間優先） |
| 自動 E2E テスト | 手動デモ優先 |
