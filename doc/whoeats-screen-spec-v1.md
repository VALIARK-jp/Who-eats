# Who eats

## 画面仕様書 v1.0（MVP）

> 本ドキュメントは「画面を作るための実務用仕様」です。  
> フローは以下で固定します。  
> 1) ユーザーの想定アクションを網羅する  
> 2) 目指す雰囲気を定義して GPT image2 でUI案を生成する  
> 3) 生成画像をもとに本チャットで実装へ落とし込む

## 1. この画面仕様書の目的

- 迷わず実装できる粒度で、画面ごとの要件を固定する
- デザイン生成（GPT image2）と実装の間で情報欠落をなくす
- MVP段階で必要十分な画面・状態・アクションを明文化する

## 2. 画面制作フロー（運用手順）

### 2.1 Step A: ユーザーアクションの棚卸し

- 画面ごとに「表示」「入力」「遷移」「例外」を分けて列挙する
- 正常系だけでなく、失敗系（権限拒否・取得失敗・0件）も書く
- Actionは「ユーザーが実際に押せる/操作できる単位」で記述する

### 2.2 Step B: 雰囲気定義の文章化

- 色・余白・写真トーン・タイポ・アイコン密度を定義する
- ブランドの人格（親しみ/信頼/軽やかさ）を言語化する
- NGスタイル（避けたいUI）も明記する

### 2.3 Step C: GPT image2で画面案を生成

- 画面単位でプロンプトを分ける（ホーム、地図、投稿など）
- 1案で終わらせず、最低3バリエーションを生成する
- 最終候補は「可読性」「押しやすさ」「実装可能性」で評価する

### 2.4 Step D: 画像を実装仕様に変換

- 本チャットに渡すときは、画面画像 + 画面名 + 目的 + 主要操作をセットにする
- 実装時は既存コンポーネント優先、なければ最小限で新規追加する
- 画像の見た目を再現しつつ、既存仕様（FR/NFR）と矛盾しないよう調整する

## 3. UIトーン（アプリの雰囲気）

### 3.1 キーワード

- 写真が主役
- 友達の実感が伝わる
- 直感的で軽い
- 温度感のあるコミュニティ
- 黒基調の没入感
- 最新感のある3D表現

### 3.2 デザイン方針（BeRealライクな軽さを参考）

- 写真カード中心。情報は詰め込みすぎず、1画面1目的を徹底
- 黒基調をベースに、テキストは白を基本とする
- アクセントは暖色またはネオン寄りのハイライトで立体感を補助する
- ホーム内で「投稿」と「マップ」を横スワイプ切替できる一体構成
- ガラス風パネル、微細グロー、奥行きシャドウで軽い3D感を出す
- ボタンは親指で押しやすいサイズ（最小44px）を確保

### 3.3 NG方針

- レストラン予約アプリのような硬い業務UI
- 文字情報過多で写真が埋もれるレイアウト
- 黒背景でコントラスト不足になる灰色テキスト
- 過剰な3D演出で可読性や操作性を下げる表現

## 4. GPT image2プロンプト雛形

### 4.1 ベースプロンプト（共通）

```
モバイルアプリ「Who eats」のUIデザイン。目的は「知らない人の評価ではなく、友達の食体験で店を選ぶ」。
写真中心、親しみやすく洗練、黒基調 + 白文字、軽い3D感（ガラス風/グロー/奥行き）。
iOSネイティブライク、実装可能な現実的UI、過剰な装飾は避ける。
1画面1目的、操作ボタンは親指で押しやすいサイズ。
```

### 4.2 画面別追加プロンプト（例）

- タイムライン:
  - `友達の投稿写真が主役のフィード。friends/near/allの切替タブ。カード内にユーザー名、店名、短文、リアクション。`
- 地図:
  - `地図上に投稿スポットピン。下部にスポットカードをスワイプ表示。ホットスポットは色で強弱。`
- 投稿作成:
  - `写真選択が最優先。店の自動候補表示、手動変更導線、自炊トグル、公開範囲セレクタ、投稿CTAを明確化。`
- 店舗詳細:
  - `店舗ヘッダー、友達の訪問情報、写真投稿グリッド、行った人数、状態ラベル（閉業/確認中）。`

## 5. 画面一覧（MVP）

- 認証（ログイン/初回登録）
- 下部ナビ5項目
  - ホーム（投稿/マップの2ペイン）
  - 友達（友達の友達を見つけてフォロー）
  - 撮影（カメラ）
  - 記録（カレンダー形式）
  - プロフィール（自分/他人）
- 店舗詳細
- 投稿作成（restaurant/home）
- フォロー・ブロック関連導線

## 5.1 下部ナビゲーション仕様（固定）

- ナビ項目は `ホーム / 友達 / 撮影 / 記録 / プロフィール` の5つ
- 初期表示はホーム（投稿ペイン）
- 撮影は中央強調CTAとして扱う（誤タップ防止の十分な余白）
- 各タブは状態保持を行い、戻ったときに直前のスクロール位置を維持する
- 未ログイン時は認証画面にリダイレクトする

## 5.2 ホーム内2ペイン仕様（固定）

- ホームは単一画面内に `投稿` と `マップ` を持つ
- 上部タブ文言は既存の「私の友達 / 友達の友達」ではなく `投稿 / マップ` に置換する
- 左右スワイプでもタブタップでも切替可能にする
- 投稿ペイン: 人の投稿を縦スクロールで閲覧
- マップペイン: 投稿に紐づくピンを地図上で閲覧
- ペイン切替時に現在の表示状態を保持する（再描画で位置を失わない）
- ホーム上部は「投稿」タイトルを表示し、その右側に通知導線を置く
- 通知種別は `コメントされました / リアクションされました / フォローされました` を基本とする
- 撮影ボタンを押すと即カメラ起動し、撮影後に投稿編集へ直接遷移する
- 投稿編集（restaurant / home 分岐）
  - 撮影直後のプレビューから投稿シートへ遷移する
  - 外食（`restaurant`）
    - 店名は位置情報から近い店舗を自動解決し、初期値として表示する（place_id も同時に確定）
    - 最小では「自動解決が成功したときのみ投稿できる」を優先する
  - 自炊（`home`）
    - 店名/店IDは不要（`posts.place_id = null`）
  - 入力項目（編集可能）
    - 一言（キャプション）
    - 誰といるか（コンパニオン/同席者）

## 5.3 マップペインのピン表現仕様（固定）

- 地図描画は地図API（Google Maps想定）を利用する
- 2Dマーカーは全店舗をオレンジ点で表示する（postedでも色は変えない）
- 3Dピンは posted 差分のみを表現する
  - 通常: `assets/3d_pin.html`
  - posted（投稿済み）: `assets/3d_pin_posted.html`
  - postedピンの顔アイコンは以下の優先順位で表示する
    - 1st: `users.icon_path`（URLまたはStorage path→signed URL）
    - 2nd: `auth.user_metadata.avatar_url`
    - 3rd: `doc/yuto.jpg`（開発用フォールバック）
- 友達訪問ピン（来店した友達アイコンのカルーセル）は、MVPでは posted差分の3D表現が優先となる（後続タスクで強化する）
- ピンタップ時の詳細は画面下から出るボトムシートで表示する
- ボトムシートには評価、友達からの一言、その店舗の撮影投稿フィードを含める

## 5.3.1 MVP運用ルール（確定事項）

- ホームの投稿表示: 自分の投稿は「作成から24時間のみ」先頭寄せで表示する
- 店舗ボトムシートの投稿表示: 店舗に紐づく投稿は永続表示とする
- マップ: viewport内は `posts + places` 由来のDB投稿ピンを優先表示し、通常ピンは不足分補完で扱う
- posted判定の正はDB（`posts.place_id` / `places.google_place_id`）とする

## 5.4 友達画面レイアウト仕様（固定）

- 友達の友達候補は2カラムグリッドで表示する
- 各カードにアイコン、名前、共通友達数、フォローボタンを表示する
- 画面上部または固定領域に `@user_code` 検索入力を配置する

## 5.5 記録画面情報量仕様（初期方針）

- カレンダー、栄養サマリ、連続投稿日数、AI提案を同一画面に表示する
- 初期は情報を全載せして検証し、利用状況に応じて後続で表示最適化する

## 5.6 プロフィール情報優先順位（固定）

- 表示優先順は `プロフィール編集 > フォロー情報 > ピン留め投稿 > 通常投稿`
- フォロー情報はフォロー/フォロワーの人数と一覧導線を含める

## 6. 画面別アクション一覧（MVP）

## 6.1 認証画面

- ログイン方式を選ぶ（Apple / LINE / メール）
- ログインを実行する
- 認証失敗メッセージを確認して再試行する
- 初回ログイン時にプロフィール初期設定へ進む
- 利用規約/プライバシーを確認する

## 6.2 ホーム画面（投稿/マップ）

- 上部タブを切り替える（投稿 / マップ）
- 横スワイプでペインを切り替える
- 投稿ペインで投稿カードを縦スクロールする
- 投稿ペインでは、自分の投稿が作成から24時間のみ先頭寄せで表示される
- 投稿詳細を開く
- リアクションする
- コメント入力導線を開く
- 投稿者プロフィールへ遷移する
- 店舗詳細へ遷移する
- マップペインでピンをタップして店舗サマリを表示する
- マップペインでは通常ピン（2Dオレンジ点）と posted差分（3Dオーバーレイ）を視認する
- マップペインでボトムシートを引き上げて詳細を確認する
- ボトムシート内で評価、友達コメント、投稿フィードを閲覧する
- マップペインのボトムシートから店舗詳細へ遷移する
- 0件状態の案内から友達/撮影へ移動する

## 6.3 友達画面

- 友達の友達候補を閲覧する
- 2カラムグリッドで候補をスクロール閲覧する
- 候補ユーザーをフォローする
- フォロー解除する
- 画面内の `@user_code` 検索を使ってユーザーを探す
- 候補プロフィールへ遷移して詳細確認する
- 共通友達数などの関係性情報を確認する

## 6.4 撮影画面（カメラ）

- カメラを起動する
- 写真を撮影する
- イン/アウトカメラを切り替える
- 撮り直しする
- 撮影結果を投稿編集に引き継ぎ、料理名（店名）/一言/誰といるかを入力する
- カメラ権限の拒否状態で案内を見る

## 6.5 記録画面（カレンダー）

- カレンダーで日付をタップする
- 日別の食事投稿サマリを確認する
- 月間の投稿傾向を確認する
- 栄養サマリを確認する
- 連続投稿日数を確認する
- AI提案（食事管理アドバイス）を確認する
- 未投稿日の案内を確認する
- 記録から対象投稿へ遷移する

## 6.6 店舗詳細画面

- 店舗基本情報を閲覧する
- 友達の訪問履歴を閲覧する
- 店舗に紐づく投稿を閲覧する
- 店舗に紐づく投稿フィードは「画像付きカード」で表示する（投稿者アイコン + コメント + 画像）
- 投稿カードから詳細へ遷移する
- 店舗状態ラベル（閉業/確認中）を確認する
- マップアプリ連携導線を開く（任意）

## 6.7 投稿作成画面

- 写真を追加/削除する
- 投稿種別を選択する（restaurant / home）
- restaurant時
  - 位置情報から最寄り店舗を自動解決して初期選択する（成功時のみ投稿できる）
  - 失敗時は送信不可（完走優先）
- home時
  - 店舗は不要（place_id は null）
- キャプションを入力する（任意）
- 評価を入力する（任意）
- 公開範囲を選択する（public/friends/private）
- 投稿を実行する（送信中はボタンを無効化）
- 投稿失敗時にリトライする

### 6.7.1 実装タスクへの分割（自炊・種別表示）

- **自炊（`home`）と外食（`restaurant`）で画面ブロックを出し分ける・完了時の肯定的文言**など: `doc/phase1/assignments/TASK-P1-26-home-cooking-post-flow.md`
- **タイムライン等の投稿カードに外食／自炊バッジ（軽量ラベル）**を付ける: `doc/phase1/assignments/TASK-P1-27-post-type-badges.md`

## 6.8 プロフィール画面

- プロフィール編集を開く（自分プロフィール）
- プロフィール編集で「アイコンのみ」を変更する（ギャラリー選択→Storageアップロード→`users.icon_path`更新）
- フォロー一覧を確認する
- フォロワー一覧を確認する
- ピン留めしたご飯投稿を閲覧する
- 投稿一覧を閲覧する
- フォロー/フォロー解除する（他人プロフィール）
- ブロック/ブロック解除する（他人プロフィール）
- 連続投稿日数やバッジを確認する

## 7. 状態別UI要件（最低限）

- ローディング: スケルトンまたはインジケータを表示
- Empty: 次アクションが分かる案内文とCTAを表示
- Error: 原因要約 + 再試行ボタンを表示
- Permission: 位置情報などの許可再設定導線を表示
- Offline: 接続不良時の簡易メッセージを表示

## 8. 画像受け渡しテンプレート（このチャット用）

以下の形式で渡してもらえれば、実装へ最短で落とし込める。

```
[画面名]
- 目的:
- 主アクション:
- 副アクション:
- 必須表示要素:
- 遷移先:
- 添付画像:
```

## 9. 実装反映ルール

- 既存仕様（`whoeats-product-spec-v1.md`）のFR/NFRと矛盾しないこと
- UI再現時は見た目だけでなく操作導線と状態遷移を優先すること
- 追加要件が出たら、まず本仕様書の該当画面に追記してから実装すること
- **個票への落とし込みと抜けチェック**は `doc/phase1/assignments/SOURCE-TO-TASK-COVERAGE.md` を正とする（画面仕様を増やしたら同ファイルの表Aを更新する）
