# TASK-P1-01: 投稿作成APIと店舗への反映（PM担当）

> **親ドキュメント**: [TASKS.md](../TASKS.md) の「TASK-P1-01」  
> **この個票は PM が配布前に片付ける用です。** メンバーの「担当タスク」として配らないでください。

---

## 目的

- ユーザーが写真付きの投稿をしたときに、**サーバー側で正しく保存**され、**店（お店）とひも付いた状態**であとから一覧に出せるようにする。
- チーム全員が「投稿データの形」を同じ前提で扱えるようにする。

---

## 説明

### アプリ上でどう見えるか

このタスクが終わると、まだ画面がきれいでなくてもよいので、**裏側では**「投稿が1件、店のID付きで保存された」という状態を作れます。ユーザーから見える画面（ボタンや入力欄）は主に `P1-02` 以降です。

### 用語ミニ辞典（このタスクだけ）

| 用語 | 意味 |
|------|------|
| **API** | アプリが「投稿してください」とお願いするときの窓口。ここを先に決めると、画面を作る人が迷わない。 |
| **place_id（プレイスID）** | Google などが付けた「このお店はこのIDです」という店の番号。投稿とお店をひも付けるのに使う。 |
| **restaurant / home** | 外食投稿か、自炊（おうち）かの区別。仕様書のとおりにサーバーが受け取れる必要がある。 |

### 前提（先に終わっていること）

- 認証で「今どのユーザーか」が分かること。
- データベースのテーブル案が `doc` にあり、PM が migration を流せること（**DBの形を変えるのはPMのみ**）。

---

## 方法

### 非エンジニアの方へ（進め方）

1. このタスクは **PM（またはエンジニアのPM代理）がサーバー・API側を作る仕事**です。
2. あなたが非エンジニアの場合: **進捗の確認**だけで十分です。次を PM に聞いてチェックしてください。  
   - 「投稿したデータは1件、一覧用のAPIで取れますか？」  
   - 「店のIDは投稿と一緒に保存されていますか？」
3. 画面の文言やボタンの見た目は、このタスクの必須ではありません（あとから `P1-22` 以降の個票で磨けます）。

### エンジニアの方へ（実装の進め方）

1. `doc/whoeats-product-spec-v1.md` の **投稿・店紐付け・公開範囲** を読み、**リクエストJSONの形**（フィールド名・型）を `doc/` に1枚書き起こす。
2. 投稿作成のエンドポイントを実装する。最低限含めるフィールドの例（名前はプロジェクトの契約に合わせる）:  
   - 写真（ファイルまたは Storage パス）  
   - 本文（任意なら null 可と明記）  
   - `restaurant` / `home` のどちらか  
   - 外食なら **店のID**（`place_id` 相当）  
   - 公開範囲 `public` / `friends` / `private`
3. 保存後、タイムライン用・店詳細用の取得APIから **同じ投稿が見える** ところまでつなぐ（「反映」の意味）。
4. エラー時は **クラッシュではなく JSON で理由が返る** 形にする（403 / 422 などは [PM-PREREQUISITES](../../pm-only/PM-PREREQUISITES-BEFORE-ASSIGN.md) の規約に合わせる）。

### 使うとよい「設定」の例（コード名はエンジニアが決める）

- **一意制約**: 同じ投稿IDが二重に作られないようにする（サーバー側）。
- **必須チェック**: 「写真が無い投稿は受け付けない」など、仕様で必須なものだけサーバーでも検証する。

## タスク

1. 仕様書と `doc` の既存設計を読み、**入力・出力のJSON** を文章化する。
2. 投稿保存のAPIを実装する（店ID・種別・公開範囲を含む）。
3. タイムライン／店まわりの取得で **同じ投稿が見える** ことを確認する。
4. メンバー向けに「APIの住所（URLパス）とサンプルJSON」をチャットまたは `doc` で共有する。
