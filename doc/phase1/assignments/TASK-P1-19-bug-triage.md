# TASK-P1-19: バグの優先付けと修正（トリアージ）

> **親ドキュメント**: [TASKS.md](../TASKS.md) の「TASK-P1-19」  
> **ブランチ名の例**: `fix/p1-19-...`（バグごとに分けてもよい）

---

## 目的

- 出てきた不具合を **重大さ順** に整理し、**ユーザー体験を壊すものから**直す。
- あとから同じバグが出ないよう、**再現手順** を残す。

---

## 説明

### アプリ上でどう見えるか

- ユーザー向けの見た目の変化はバグごとに違う。このタスクは **「直す作業の進め方」** が中心。

### 用語ミニ辞典（このタスクだけ）

| 用語 | 意味 |
|------|------|
| **トリアージ** | 病院の選別のたとえ。**どれから手を付けるか**を決めること。 |
| **Critical** | アプリが落ちる・データが壊れるなど、**最優先**。 |

### 前提（先に終わっていること）

- Issue またはスプレッドシートに **バグ一覧** がある（PM）。
- 優先度の定義（Critical/High/…）が書いてある。

---

## 方法

### 非エンジニアの方へ（進め方）

1. 各バグについて **「再現手順」** をスマホで撮影または文章で書く（何タップ目かまで）。
2. **期待した動き** と **実際の動き** を1行ずつ書く。
3. 直ったかどうかを **同じ手順で再チェック**する。

### エンジニアの方へ（実装の進め方）

1. PMが並べた順に Issue を **1件ずつ** クローズする方針。修正が大きい場合は **PRを分ける**。
2. 修正内容は **`git commit -m` に Issue 番号** を含めると追いやすい（チームルールに従う）。
3. 回帰が怖い箇所は **該当ウィジェットのテストを1本** 追加する（無理なら手動チェック項目をPRに書く）。

### 使うとよいウィジェット・プロパティの例

（バグ内容によるため省略。必要なら **デバッグ用 `print` はコミットしない** 方針を守る。）

---

## 確認

- [ ] 対象Issueの **再現手順が再現しなくなった**。
- [ ] 新しいクラッシュや副作用が **明らかでない**（あればPRに記載）。
- [ ] PR本文に **Issueリンク** または再現手順の要約がある。

---

## タスク

1. バックログを読み、着手順を確定する。
2. 1件ずつ修正PRを出す（まとめすぎない）。
3. 非エンジニアによる確認を受ける。
4. PMが優先度を更新する。
