Who eats

続く食の記録で、偏らない食生活を。

一人暮らし大学生の食生活を、友達との共有と地図で支える食事SNS

Flutter / Supabase / PostgreSQL / Google Maps

基礎工学 PBL（情報工学 A）— 1班 · 中間発表

社会課題：一人暮らしと偏食

食事管理が「完全な自己責任」へ — 一人暮らしで食生活が崩れやすい

  • 自炊が続かない — 手間・コストで挫折しやすい
  • 外食・コンビニに偏る — 同じ店・同じ弁当になりがち
  • 振り返りができない — 何を食べたか見えない
  • 一人記録は続かない — 習慣化しにくい

切実性：大学生の「食生活の乱れと偏食」／普遍性：単身生活開始時に広く発生

自炊・外食を同じ流れで投稿し、共有することで食の記録を続けやすくする

気軽な食事投稿

自炊も外食も、写真と短いコメントだけで記録。カロリー入力の重さを排除し、SNS感覚で「続く記録」を実現します。

友達フィード

友達の食事から刺激を受け、継続の動機づけに。いいねやコメントの反応が、一人作業の孤独感を解消します。

地図ピンによる発見

外食投稿は地図上のピンに。友達が実際に行った信頼できる店を見つけることで、コンビニへの偏りを防ぎます。

  • Backend: Supabase
    Auth / PostgreSQL / Storage / RLS
  • Google Maps Platform

1回の投稿を、多角的に再利用するデータ設計

  • 画像の分離保存
    画像本体は Storage へ保存し、DB には `storage_path` のみを保持して軽量化。
  • 自炊と外食の統合管理
    外食投稿は Places API の店舗情報と紐付け(`place_id`)永続化。自炊は `place_id = null` として同じ `posts` テーブルへ。
  • 安全な表示制御
    保存されたデータは、常に Row Level Security (RLS) を通過し、閲覧権限のある投稿だけがホームフィードや地図に配信されます。

信頼性とセキュリティ設計

信頼性は「友達ベースのサービス設計」と「DBレベルの技術設計」の2層で担保します。

サービス設計上の制御

  • 相互フォロー — 友人関係に基づく情報を優先
  • 公開範囲 — Public / Friends / Private
  • ブロック — 双方向に表示・反応を制限

技術基盤での実装

  • RLS — DB 側で `auth.uid()` 等を判定
  • RPC — 2ホップ取得等をサーバー側集計
  • API キー — `.env` と `dart-define` で管理

DB設計とクリーンアーキテクチャ

将来の AI 分析や機能拡張に耐えうる分離設計を行っています。

  • レイヤーアーキテクチャ
    Presentation, Domain, Repository, DataSource に層を分離。UIとDB接続を直接結びつけない。
  • Mock DataSource の準備
    API制限やネットワーク障害時でもデモを継続できるフォールバック機構。
  • 正規化された拡張可能DB
    users, posts, places 等に正規化し、将来の「AIによる食事傾向分析」の基盤とする。
